# Architecture

## Execution contract

TypeScript owns the caller. Today the React Native UI submits a timer call or a Google Maps batch. A future TypeScript agent loop can submit one call, inspect its result, and decide what to do next. It can also submit a batch when it already knows the dependencies. The same API supports both flows.

A task has a caller-chosen ID and up to 32 typed calls. The Kotlin boundary validates arguments, dependency cycles, and result references before accepting any work. An app search returns a list of supported installed apps. An `apps.open` or `apps.observe` call may bind that list to its target if it contains exactly one app. Empty and ambiguous searches remain visible to the caller, which can refine the query or pick a specific supported app. `after` provides ordering. A dependency satisfied by `ISSUED` means the request was dispatched. For evidence-dependent decisions, inspect the structured result.

Kotlin accepts one active task and runs up to four ready calls at once, with one foreground action at a time. `FAIL_FAST` stops scheduling after the first failed or unknown outcome is recorded. `CONTINUE_INDEPENDENT` skips dependent calls and lets unrelated calls proceed. Cancelling skips queued and paused calls. Already started actions can finish recording their results. There is no rollback for an external action.

## State and recovery

```text
QUEUED → RUNNING → SUCCEEDED | ISSUED | FAILED | UNKNOWN
   │         │
   └─────→ PAUSED → QUEUED
QUEUED or PAUSED → SKIPPED
```

The executor writes each transition to a private SQLite journal. In particular, `RUNNING` is committed before an adapter can issue a side effect. Submitting an identical request with the same ID returns its saved state. A different request needs a new ID.

Starting a timer uses `AlarmClock.ACTION_SET_TIMER` and can report `ISSUED`. The Clock app owns the countdown and the intent provides no verification callback. Opening a supported app verifies the target package against Android's active Accessibility window where available. The evidence establishes which app had the active window at the recorded time.

When Android kills the process, the app reconciles interrupted work when the verifier reconnects or the caller next reads or sends a command. An interrupted timer or app launch becomes `UNKNOWN`. An app launch can include window evidence collected within a one-second window while the verifier reconnects. That observation describes the active app at recovery time. Only recorded successful or issued steps satisfy dependencies. Inspect the external outcome before intentionally submitting another action. Unstarted calls and interrupted reads require confirmation to continue. The executor does not replay interrupted side effects.

The journal doubles as a device-local record of action calls. Each task keeps its ID, its submitted steps with their exact inputs, and the recorded state of each step. `tasks.list(limit, before)` pages through tasks in submission order, newest first, up to 20 at a time. Pass the last task ID from a page as `before` to read the next one. Listing reconciles interrupted work using the executor’s recovery rules and never dispatches actions. Typed adapters interpret their own steps. To repeat an earlier call, submit its inputs under a new task ID.

## Conversation

The debug agent keeps one device-local conversation in the task database. A prompt is saved as a `RUNNING` turn before inference, and the final reply or error is saved against the same turn as `COMPLETED` or `FAILED`. Turns run in JavaScript, so a new JavaScript runtime marks any turn still running as `INTERRUPTED` and never replays it. Tasks submitted by agent tools record the turn ID, so a turn shows the task journal's own evidence for its calls. UI workflow actions are not journaled and are not linked. Replies from screen-assisted turns are saved; observations are not.

`conversation.read(limit, before)` pages through turns newest first, like `tasks.list`. Failed, interrupted and running turns stay visible but are not sent to the model. The schema version stays at 1 so earlier builds can open the database, and rows from the earlier `conversation` table are copied once and left in place.

If saving a turn's reply or error fails, the app keeps the outcome and saves it again before the next prompt starts. Saving the same outcome twice succeeds, so a save that landed without an acknowledgement is safe to repeat. Inference and tools never run again for that turn.

## Sign in with ChatGPT

The app signs in with ChatGPT on the phone through the [Sign in with ChatGPT](https://developers.openai.com/siwc/token-sharing-open-source/sign-in) authorization code flow with PKCE. The `chatgpt` Kotlin package does all OAuth and model traffic, and JavaScript only sees account IDs, model replies and usage counts. Before opening the browser, `Loopback` listens on `127.0.0.1` on an ephemeral port, and the authorization request names `http://127.0.0.1:<port>/auth/callback` as the redirect. The listener answers only `GET` requests on that path with the exact `Host` and a matching `state`, compared in constant time. Other requests get an error page and leave sign-in waiting. **Cancel sign-in**, a denied consent and a 10-minute timeout end it.

The first sign-in registers the app with `dynamic_agent_client` and saves the issued client ID before exchanging the code, so a failed exchange reuses the registration once. The ID token is checked against the issuer's JWKS (RS256, issuer, audience, nonce, expiry and issue time with 5 seconds of tolerance), and its subject becomes the account. A later sign-in must return the same subject, so a stale voice turn or shared history cannot reach another account. Sign-in fails unless the grant includes `chatgpt.tokens.use.direct`; the next attempt asks for consent again.

`Vault` keeps the registration, the account and the tokens in app-private preferences, encrypted with AES-GCM under a non-exportable Android Keystore key. If the key is lost, the app starts signed out. A mutex serializes refreshes, which start within a minute of expiry, honor `earliest_refresh_at` and finish even if the caller is cancelled. Refreshed credentials are saved only after validating any returned ID token. Verification failure requires sign-in again. A refresh rejected as expired, reused or revoked clears the tokens and asks the same account to sign in again. A request rejected with 401 refreshes once and retries. **Sign out of ChatGPT** clears the tokens, then revokes the refresh token, retrying once on a server or network error. If revocation is not confirmed, the app asks the user to disconnect Android Agent in ChatGPT Settings. The registration and account survive sign-out. Error messages come from fixed text keyed by OAuth and API error codes; provider messages, tokens and replies are never shown or logged.

Inference posts the instructions and input to the Responses API with `store: false` and `stream: true`, on the first model listed in the account's catalog, and reads `context_window` from the same catalog. The reply streams over server-sent events, and `response.completed` reports the input tokens. The companion stays available as a fallback: a saved connection is either a direct account or a companion session, and both run through `connectedModel` in `src/prompts.ts`.

## Conversation history

Each new turn records its connection owner. Direct sign-in includes completed turns for that ChatGPT account across app restarts, failures and switches to the companion. Older turns without an owner require explicit history sharing. A companion session starts a new scope on every pairing, because the app does not know the companion's account. These turns were already sent to that owner, so they need no consent and go without the checkpoint, newest first within the history budget. Sharing earlier saved history with a connection requires opt-in on each connection. The companion validates the sign-in session on every inference request and invalidates it when sign-in starts again. Screen-assisted replies can be included when history is shared. Model input starts with the same instructions on every request, then the latest checkpoint summary, then every completed turn after the turn the checkpoint covers, word for word. Text-only requests between compactions extend the previous initial request, preserving its reusable prefix. Screen-sharing and tool-loop messages are turn-local and can shorten the prefix a later request can reuse. The instructions always list the screen tools, so turning screen sharing on or off does not change the reusable prefix. The setting is persistent and off by default (`ScreenConsent`); with it off, the native tools refuse screen actions and the agent returns a setup error. Turn-local screen observations and tool results are never stored in history.

`contextBudget` in `src/agent.ts` budgets requests in tokens for the selected model. A direct sign-in reads the window from the account's model catalog. On **Check connection** the companion reports that model's `context_window` from the raw model catalog, because the DevKit's model list keeps only names. When the catalog states no window, the app says so and assumes a deliberately small 32,000-token window. Of the window, up to 32,000 tokens (a quarter for small windows) stay free for reasoning and the reply. Stored history may use three quarters of the rest, leaving the remainder for the current prompt, screen tools and tool results. Tokens are estimated as UTF-8 bytes of the request body divided by three; English averages about four bytes per token, so the estimate errs high. Nothing runs the model's tokenizer. Separately, every request stays under the companion's 2,000,000-byte HTTP body bound, which limits history for models with very large windows. Every model call, including each step of the tool loop and the summary request, is checked against both limits first. If the current request alone is too large, or tool results push it over, the turn fails before that call without running more tools. When stored history passes 80% of its share, the app sends that same input plus a summary request through the normal inference route. Only a lone `finish` reply counts, and no tools run. The summary and its coverage are saved in one transaction, and coverage only moves forward. If summarizing or saving fails, the previous checkpoint stays. If stored history still exceeds its share, the request sends the newest turns that fit and leaves the checkpoint unchanged. This capacity trigger stays as the fallback for idle compaction.

Idle compaction runs the same summary request in the background, so the next prompt can start from the checkpoint while the provider may still hold the previous prefix in cache. It is scheduled in `src/idleCompaction.ts` when the latest prompt request was reported above 200,000 input tokens, and runs once two minutes after the app became idle in the foreground with history shared. The companion reports input tokens only from a live provider connection. A direct sign-in reports them from every streamed reply, and its background request runs like a prompt request whose reply is dropped once cancelled. A new submission, a session or sharing change, or leaving the foreground cancels it, and a summary that arrives after cancellation is discarded. A checkpoint write already submitted to Android can finish. Each reported context gets one attempt. An interrupted attempt can retry when the app returns to the foreground if its usage is still current. The request is live-only: `companion/modelRoute.mjs` runs it only on an already open, idle connection, never opens one and never falls back, so it fails when the provider closed the connection. Prompt requests take priority and cancel it. `companion/openaiSocket.mjs` keeps one reused OpenAI Responses WebSocket and sends full input with `store: false`, because the warm-cache probes saw cache hits only on a reused socket. The unmodified DevKit exposes no access token or socket. `companion/devkit-responses-socket.patch` adds `openResponsesSocket`, which authenticates the handshake with the DevKit's refreshed credentials and closes its sockets on sign-in, profile change or disconnect; the token never reaches the companion. With an unpatched DevKit every request uses the HTTP stream, no usage is reported and idle compaction never runs. The companion checks the session again right before dispatching, so a sign-in that starts while a request is waiting cannot send the old history under the new session. It logs the input and cached token counts of each live request, never their content.

The executor lives in the Android application scope and can record results after the React Native Activity pauses. A foreground handoff, lock, or loss of window focus in the confirmed Activity requires an explicit **Continue task** before another UI action can run. The first slice never injects gestures into the target app. It records the app-window observation during the handoff when available. The user can keep using their phone while read-only calls finish.

## Voice turns

On API 36 and later, Android Agent can be the default digital assistant. Voice setup downloads the pinned Parakeet archive, checks its SHA-256 and installs the model to app-private storage. Transcription uses the installed files offline. `AssistantService` records one utterance, transcribes it offline and hands the final transcript to `VoiceTurns`, which starts the `VoiceTurn` headless task in the shared React Native runtime. A cold runtime starts without an Activity, so Android Agent never comes to the foreground. `src/voice.ts` runs the transcript through `ask` in `src/prompts.ts`, the same path as typed prompts, so it saves a `RUNNING` turn first, uses the saved connection and history consent, and records the reply or failure in the same journal.

Typed and voice prompts share one runtime-wide lock. A voice turn that arrives while another prompt is running is not queued: the overlay reports that Android Agent is busy and no turn is saved. The native journal refuses a second running turn as a second guard. Without a saved connection the turn is saved as `FAILED` with "Sign in with ChatGPT in Android Agent." Any failure clears the saved connection and its history consent, as it does for typed prompts, and keeps the history scope.

The companion pairing code, the current connection, the history consent and the history scope live in app-private `SharedPreferences` so a headless runtime can read them. ChatGPT credentials stay in the encrypted vault. Backups are disabled.

A voice turn is text-only unless screen sharing is on. With it on and another app in front after transcription, the service records a `ScreenGrants` grant for that app without asking, and the turn ends without screen access if that app has changed. The grant covers that one turn only: `VoiceTurns` revokes it when the turn finishes, and it expires with the 180-second turn timeout. Asking from the home screen runs the turn text-only.

A shared voice turn starts by reading the source app. It may then open up to four apps in total, one session at a time. Kotlin launches each app from the Accessibility service with an API 36 background-start option, so Android Agent stays in the background. The latest observation of each app stays in the model context, so the source text survives a switch. The timer and other Activity-bound actions still fail with an error telling the user to open Android Agent.

Pending voice turns are held only in memory. If the process dies, the next runtime marks the turn `INTERRUPTED` and nothing replays. The headless task ignores a repeated delivery of the same turn ID.

While a turn runs, a blue working dot replaces the listening dot. A reply that arrives while that dot is still on screen counts as quick and replaces it with a card that stays until tapped. If the user taps the dot away or invokes the assistant again, the turn counts as long-running and its reply or failure posts a notification instead. This boundary uses no fixed threshold. Each turn logs its duration, whether it failed and whether it was quick under `AssistantSpeech`, never the transcript or reply, so a time threshold can be chosen from measurements later.

## Permissions and workflows

The current allow-all mode covers the typed timer and supported app operations. Debug builds include an opt-in Accessibility service for foreground app evidence. It reads the active window's package and persists only the supported target, whether it matched, and when. Search queries and timer durations are local task inputs. With screen sharing enabled, an active agent turn can also request visible text and controls from the verified foreground window. Direct ChatGPT connections can send a screenshot with that request.

Claude Code dynamic workflows show how JavaScript can branch on results and coordinate callers with a small set of allowed primitives. On Android, a comparable experiment could expose only the typed calls and journal reads, with results checkpointed by call ID so restarting a script does not replay side effects. [Claude dynamic workflows](https://platform.claude.com/cookbook/claude-agent-sdk-08-dynamic-workflows)

Repository-authored TypeScript can use regular control flow around `tasks.submit` and `tasks.read`, or hand a known dependency group to Kotlin. A model-authored workflow would need an isolated runtime with scoped tools, time limits, and a clear lifecycle. The same typed executor API can be the boundary for evaluating that approach later.

The timer and app launches require a resumed Android Agent Activity and an unlocked, interactive screen. For future deferrable work, consider WorkManager. A user-visible foreground service or assistant entry point has separate Android requirements. [Background activity launches](https://developer.android.com/guide/components/activities/secure-bal) · [VoiceInteractionService](https://developer.android.com/reference/android/service/voice/VoiceInteractionService)

## Foreground UI workflows

The sideloaded debug build can start a TypeScript workflow against a selected Android package. The same Kotlin adapter opens the app, reads a bounded Accessibility snapshot, and requests click or text-entry actions supported by the selected element. On Android 13 and later the launch uses a package-scoped intent sender. On older versions the target must already be visible to the app. The Maps demo's selectors live in TypeScript.

Each element label keeps up to 200 characters. Longer text, such as a video description, keeps up to 4,000 characters while a 16,000-character snapshot budget lasts.

The agent loop counts attempted and failed tool calls per turn and logs only those counts. A call that failed is refused if it is repeated on an unchanged screen, and the turn stops after six failures.

Each action consumes its snapshot. Before dispatch, Kotlin checks the active package, window, target, and matched label. A stale result means the action was never issued, so the caller can re-observe and retry its selection. An accepted action is a dispatch receipt. The workflow checks the next screen for evidence of the result.

A session is started from Android Agent while it owns the foreground and lasts at most one minute. The expected target-app handoff lets the script continue. A detected switch away from the app, a reported touch interaction, or an unavailable screen ends the session or blocks dispatch. Touch reporting depends on Android and the active accessibility configuration. Return to Android Agent to start again. A voice turn with a screen grant can start a session from the background instead; see [Voice turns](#voice-turns). Only explicitly started workflows receive snapshots. Snapshot data stays in memory. The step journal still covers task batches. UI workflow sessions end on process death and scripts do not replay automatically.

`get_screen` reads the session window and, on API 34 and later, takes a screenshot of it with `takeScreenshotOfWindow` from the Accessibility service. Capture runs only when the model calls the tool during a turn; nothing polls. The capture is discarded and retried, for up to 5 seconds, if the window or accessibility tree changes during capture. This check detects changes to the tree and can miss pixel-only changes. Secure windows fail with an error. The JPEG is scaled to at most 1568 px on its longer side and saved by `Screenshots` under `noBackupFilesDir/screenshots`, in a directory keyed by a hash of the connection owner. IDs are opaque and timestamped (`s-yyyyMMdd-HHmmss-xxxxxx`), at most 24 are kept across owners, and the oldest is dropped first. `list_screenshots` and `read_screenshot` read only the current owner's files by ID. Turning screen sharing off and ChatGPT sign-out delete the store. Only the latest image stays in the model input; earlier ones are replaced with a note to read them again by ID. Kotlin adds the image to the direct Responses request as an `input_image` part, so JavaScript never holds the bytes. The companion strips images and receives the accessibility text only. Images and screen text are never logged.

## Isolated display feasibility

A normal app can create a private, own-content virtual display. Starting an activity on it also requires that Android allow the activity on that display. `ActivityOptions.setLaunchDisplayId` is available from API 26 and requires the device’s secondary-activity display feature. On API 29 and newer, use `ActivityManager.isActivityStartAllowedOnDisplay` with the actual target intent and display. Android restricts cross-app launches on untrusted virtual displays, so a display owned by the app is insufficient for general third-party UI automation. [ActivityOptions](https://developer.android.com/reference/android/app/ActivityOptions#setLaunchDisplayId(int)) · [AOSP activity launch policy](https://source.android.com/docs/core/display/multi_display/activity-launch)

Trusted display and companion app-streaming paths have separate system permission and association requirements. Explore ADB or Shizuku as opt-in development paths on real hardware. ADB-backed Shizuku runs with shell permissions, which vary by Android build. Wireless setup requires Android 11 or newer, and an ADB-backed service must be started again after reboot. Treat app launch, readable output, input targeting, and concurrent use of the main display as separate pass criteria. Verify each on a stock Pixel 9 for the intended apps and Android build before offering the mode. [AOSP virtual-device sample](https://android.googlesource.com/platform/development/+/35af5c328/samples/VirtualDeviceManager/) · [Shizuku setup](https://shizuku.rikka.app/guide/setup/)

Visual or Accessibility-based integration requires its own review. Google Play prohibits general autonomous planning and execution through its Accessibility API, with a narrow exception for verified accessibility tools serving people with disabilities as their core purpose. Plan the Play build around explicit integrations and narrowly scoped APIs. [Google Play AccessibilityService policy](https://support.google.com/googleplay/android-developer/answer/10964491)
